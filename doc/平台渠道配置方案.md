# 平台渠道配置方案

状态：已按确认方案实施，通过自动化测试、接口联调和浏览器业务验收；未执行真实第三方发送。更新日期：2026-10-11。

涉及 `ops-agent-api`、`ops-agent-web`、`ops-notify-gateway`。本文件统一维护跨项目约定，实施后将已交付行为同步到各项目接口、配置及接入文档。

## 目标与边界

- 平台维护渠道，各公司只能查看、修改自己的渠道。
- 不同公司、部门共用一个网关实例，通过全局唯一的 `channel` 路由。
- Jenkins、Alertmanager 等调用方直接调用网关；网关配置文件维护单一入站 Token，不按公司区分 Token，也不绑定 Token 与渠道。平台只管理渠道并提供配置读取接口，不转发通知请求。
- 网关默认保留本地 YAML 独立运行模式，不引入数据库或管理后台。
- 平台模式使用内存运行配置和本地 YAML 恢复文件，不引入 Redis 或其他缓存服务。
- 第一阶段不做队列、发送失败重试、通知历史、静默、渠道删除或在线模板编辑。

## 职责与调用链

```text
公司管理员 → ops-agent-web → ops-agent-api → notification_channels
Jenkins / Alertmanager / Generic 调用方 → 通知网关 → 钉钉 / 飞书
通知网关 → ops-agent-api 专用读取接口 → 完整渠道快照（定时拉取）
```

平台模式下，通知发送和配置读取是两条独立链路：调用方携带网关入站 Token 直接提交通知请求；网关使用独立的平台专用读取 Token 定时拉取渠道配置。拉取配置只更新运行配置，不触发消息发送；收到通知请求后，网关按 `channel` 查找配置并发送。独立 YAML 模式保留现有接入方式。

| 项目 | 职责 |
|---|---|
| ops-agent-api | 渠道存储、租户管理权限、敏感字段加密、操作审计、专用读取接口 |
| ops-agent-web | 渠道列表、新增、编辑、启停 |
| ops-notify-gateway | 校验入站 Token、同步配置、维护内存快照与本地恢复文件、按渠道转换并发送消息 |

平台沿用现有分层、租户权限和 AES-GCM 加密组件；通知渠道单独建模块，不并入现有 Jenkins/GitLab 集成实例。网关复用 `ChannelStore`、渲染器和发送器工厂。

## 平台数据与管理权限

新增 `notification_channels` 表，结构维护在平台初始化基线及 `sql/upgrades/011_notification_channels.sql`。

| 字段 | 规则 |
|---|---|
| `id` | 主键 |
| `tenant_id` | 所属公司，由后端从登录上下文取得 |
| `code` | 对应调用参数 `channel`，全局唯一，创建后不可修改 |
| `name` | 可修改的显示名称 |
| `platform` | `dingtalk` / `feishu`，创建后不可修改 |
| 加密配置、nonce | 保存 webhook、secret，复用现有加密组件 |
| `at` | 默认接收人 |
| `enabled` | 是否启用 |
| 创建、更新时间 | 沿用平台惯例 |

- 对 `code` 建全局唯一约束，不能仅使用 `(tenant_id, code)` 联合唯一；为租户列表查询配置索引。
- 建议使用 `company_a_ops` 等名称，但租户归属只依据 `tenant_id`，不解析名称前缀。
- 第一阶段不支持渠道转移租户或资源域独立授权，只向具有租户范围权限的用户开放管理。
- 列表按租户过滤；详情、修改和启停按 `tenant_id + id` 校验，不能仅过滤列表。
- 管理接口不返回 webhook、secret 明文，只返回 `has_webhook/has_secret`；更新时省略敏感字段表示保留，非空值表示替换，secret 空字符串表示清空，webhook 不允许清空。飞书拒绝非空 secret，禁止将掩码写回。
- 审计只保留渠道标识和安全的变更摘要，不记录敏感配置。

## 接口与页面

管理接口沿用平台统一响应和权限机制，权限为 `notification_channel:view/create/update`。

| 方法与路径 | 用途 |
|---|---|
| `GET /api/v1/tenant/notification-channels` | 分页列表 |
| `POST /api/v1/tenant/notification-channels` | 创建 |
| `GET /api/v1/tenant/notification-channels/:id` | 管理详情，不返回敏感明文 |
| `PUT /api/v1/tenant/notification-channels/:id` | 修改配置、启停 |
| `PUT /api/v1/tenant/notification-channels/:id/enabled` | 仅更新启用状态，不覆盖名称、接收人或敏感配置 |
| `GET /api/v1/internal/notification-channels` | 网关读取全部授权渠道的完整快照，包含启用状态 |

管理端增加查看、创建、修改权限。前端新增“通知渠道”页面，复用菜单权限、请求封装和表单模式。

专用读取接口使用独立服务 Token，允许共享网关跨租户读取渠道，但不允许写入或访问其他业务。该凭据由服务端部署配置管理，不交给浏览器或通知调用方，不复用管理员登录 Token 或网关入站 Token。接口默认使用 HTTPS；仅本机联调的 `localhost`、`127.0.0.1`、`::1` 允许 HTTP，禁止浏览器和代理缓存；网关按下述规则持久化 YAML 快照。管理和读取接口使用不同 DTO。

平台通过环境变量 `NOTIFICATION_CHANNEL_READ_TOKEN` 配置读取凭据，网关将同一凭据配置在 `channel_source.platform.token`。未配置读取凭据时，平台快照接口拒绝访问（401），不影响其他 API 启动。成功响应为 `{code: 200, message: "操作成功", data: {version: 1, channels: [...]}}`，每项包含 `code/platform/webhook/secret/at/enabled`。一次最多 10000 个渠道，完整响应不超过 8 MiB。仅返回有效租户的渠道，包含渠道自身的禁用状态；租户停用或归档后在下一次成功同步时移除其渠道。

第一阶段一次返回完整快照，不分页，不做增量同步或推送。失败、截断或不完整的响应不能当作成功快照；合法空列表表示清空运行渠道。

## 网关双模式

| 模式 | 配置来源 | 平台依赖 |
|---|---|---|
| `file`，默认 | 本地 YAML | 无 |
| `platform` | 定时从平台同步，发送时读取内存 | 同步依赖平台，故障时使用最近成功配置 |

通过 `channel_source.mode` 选择来源，省略时默认 `file`。同一个 YAML 文件允许保留两套配置；只读取和校验当前选中的来源，不合并渠道，不自动切换，修改模式后重启。平台模式忽略本地 `channels`，失败时不回退 YAML。现有通知接口及 `channel` 参数保持不变。

```yaml
auth:
  enabled: true
  token: "replace-with-inbound-token"
channel_source:
  mode: file
  platform:
    url: https://ops.example.com/api/v1/internal/notification-channels
    token: "replace-with-platform-read-token"
    recovery_file: /var/lib/ops-notify-gateway/channels.snapshot.yaml
channels:
  ops_alert:
    platform: dingtalk
    webhook: https://oapi.dingtalk.com/robot/send?access_token=example
    enabled: true
```

平台模式要求完整读取接口 URL（HTTPS，或主机名精确匹配 `localhost`、`127.0.0.1`、`::1` 的 HTTP）、独立读取 Token、恢复文件路径，不需要恢复文件加密密钥。可省略 `sync_interval_seconds` 和 `timeout_seconds`，分别默认 30 和 5 秒。本地模式不要求这些平台配置有效。

复用 `ChannelStore` 作为发送流程的读取入口，平台实现从当前内存快照查找，不发起 HTTP 请求；增加错误返回值，区分尚无可用快照与渠道不存在。配置工厂在启动时选择实现，发送流程继续复用现有代码。

### 同步与持久化

- 默认每 30 秒拉取一次，单任务串行同步，设置请求超时，避免旧结果覆盖新结果。
- 完整校验快照后，原子替换内存配置，再写入本地 YAML 恢复文件。通知只读内存；一次请求使用同一份快照，Alertmanager 拆分发送共用该次结果。
- 文件保存采用同目录临时文件加原子替换；失败时保留旧文件，但不回退已更新的内存，避免已禁用渠道继续发送。后续成功同步继续尝试保存。
- 同步失败保留当前配置；完整快照中的禁用、渠道移除和合法空列表均必须生效。
- 内存与文件是一份配置的运行状态和持久副本，不分别设计 TTL、淘汰策略或人工编辑入口。

### 启动与故障处理

| 场景 | 行为 |
|---|---|
| 启动时平台可用 | 使用平台快照并更新恢复文件 |
| 启动时平台不可用、文件有效 | 加载本地快照，后台继续同步 |
| 平台不可用且无有效文件 | 进程继续同步，但不就绪；通知返回配置不可用 |
| 运行中同步失败 | 使用最近成功配置继续发送，暴露同步异常 |
| 文件损坏、格式错误或来源不匹配 | 拒绝加载，不当作有效配置 |
| 文件保存失败 | 当前内存继续生效，暴露持久化异常和上次成功保存时间 |

存活与就绪检查分开：存在有效快照即可就绪，合法空快照也视为已完成初始化；同步异常不应触发反复重启。记录最后成功同步时间、同步状态和持久化状态，日志与健康信息不得泄露敏感配置。

`GET /ping` 检查存活，`GET /ready` 返回就绪、同步及持久化状态。无有效快照时就绪和通知接口返回 HTTP 503、业务码 50301；有旧快照的同步故障保持就绪，通过状态及最后成功时间识别故障。

本地恢复文件使用明文 YAML，记录格式版本、配置源地址和同步时间，恢复时校验结构、版本、来源及渠道配置。文件权限为 `0600`，新目录为 `0700`，不提交 Git；无需额外加密密钥。仅允许单个 YAML 文档，文件上限 32 MiB。容器部署必须挂载持久卷，各实例独立维护文件，不依赖共享文件写入。第一阶段只保留最近一次成功保存的快照，不提供历史版本管理。

### 发送与校验

- Jenkins、Alertmanager 等调用方携带统一的网关入站 Token 和 `channel` 直接调用现有通知接口；网关校验 Token 后按渠道配置发送，不做公司级发送授权，平台不参与通知请求转发或发送归属校验。
- 渠道不存在或禁用时明确拒绝；没有有效快照时返回配置不可用，不泄露平台响应。
- 同步超时与发送超时分别控制，通知请求不等待平台同步。
- 平台模式暂用网关按来源和通知平台选择的默认模板；独立模式保留已有模板配置。
- 平台与网关校验 webhook 的 HTTPS 协议、平台域名及接收人格式；出站请求不能通过重定向绕过地址限制。
- 网关已支持飞书可选加签：secret 非空时加签，为空时不加签；平台表单及后端校验需允许该配置。

## 运行策略与限制

1. **调用方直连，网关统一鉴权。** 平台模式开启网关入站鉴权，使用网关配置文件中的 `auth.token`，Jenkins、Alertmanager 等调用方通过各自的私有配置持有同一 Token。网关不区分公司 Token，不绑定 Token 与渠道；平台的租户权限仅用于渠道管理，不限制网关发送。持有入站 Token 的调用方可以向指定的有效渠道发送。入站 Token 不下发浏览器，不与平台专用读取 Token 复用；平台专用读取 Token 仅供网关拉取配置，不提供给通知调用方，私有配置不入库。
2. **旧配置优先保障发送。** 平台失联时继续使用最近成功配置，不因配置年龄自动停发，同时持续暴露同步异常。配置修改在下一次成功同步后生效；正常情况下约一个同步周期加请求耗时，故障期间无法保证禁用及时生效，已在途请求也可能继续发送。
3. **启停影响整个渠道。** 会影响该渠道上的全部消息，不能替代只屏蔽部分告警的维护静默。
4. **恢复以文件成功保存为准。** 落盘失败后重启可能恢复较旧配置，包括旧的启用状态；本地文件丢失且平台不可用时，无法恢复发送。配置源容错不代表发送失败重试。

配置与错误码细节维护在网关配置说明和接口文档；渠道管理协议及权限维护在平台接口文档。平台配置读取端点在正式部署时由部署层提供 HTTPS，网关不跳过证书校验；仅固定的本机主机白名单允许 HTTP 联调。
