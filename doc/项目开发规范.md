# 项目开发规范

## 一、项目目标

`ops-notify-gateway` 是统一运维通知网关，用于接收运维系统事件并路由到不同通知平台。

第一版支持：

- Alertmanager 告警通知
- Jenkins 构建通知
- Generic 通用通知
- 钉钉机器人
- 飞书机器人
- 钉钉加签
- 基于 `channel` 的通知路由
- Token 鉴权

第一版不支持：

- 数据库存储
- 通知记录查询
- 管理后台
- 异步队列
- 失败重试
- 多租户权限模型
- 对接 `ops-agent-api`

## 二、架构原则

核心链路：

```text
外部系统 -> api -> service -> channel router -> sender -> 钉钉/飞书
```

设计原则：

- 对外系统只发送标准事件，不直接持有通知平台密钥。
- 服务端统一维护 channel、webhook、secret、模板和默认 @ 人规则。
- 输入来源适配和发送平台适配分离。
- Jenkins、Alertmanager、Generic 属于事件来源逻辑，放在 `service/`。
- 钉钉、飞书属于发送平台适配，放在 `pkg/sender/`。
- 第一版不引入数据库，避免把网关做重。

## 三、技术栈

| 能力 | 选型 |
|---|---|
| 语言 | Go |
| HTTP | Gin / `github.com/tiamxu/kit/http` |
| 日志 | `github.com/tiamxu/kit/log` |
| 配置 | YAML |
| 模板 | Go `text/template` |
| HTTP Client | 标准库 `net/http`，统一超时 |
| 数据库 | 第一版不使用 |

禁止未经确认新增大型依赖、ORM、消息队列、缓存或任务调度组件。

## 五、分层职责

### api

职责：

- 解析 JSON、Query、Header。
- 做基础参数校验。
- 调用 service。
- 返回统一响应。

禁止：

- 编排发送流程。
- 直接调用钉钉、飞书 sender。
- 读取或拼接 webhook、secret。

### service

职责：

- 校验业务字段。
- 按 channel 获取发送配置。
- 将来源事件转换为统一通知消息。
- 选择模板。
- 调用 sender。

禁止：

- 处理 HTTP 响应。
- 依赖 Gin 上下文。
- 输出敏感配置到日志。

### types

职责：

- 请求结构。
- 响应结构。
- 配置结构。
- 内部 DTO。

禁止：

- 写业务逻辑。
- 写发送逻辑。

### pkg

职责：

- 发送平台适配。
- 模板渲染。
- 脱敏。
- HTTP client。
- 错误码。

禁止：

- 放 Jenkins、Alertmanager、Generic 事件转换。
- 放 channel 路由业务。
- 依赖 api 或 service。

## 六、pkg 设计规范

### pkg/sender

`pkg/sender` 提供统一发送接口：

```go
type Sender interface {
    Send(ctx context.Context, message Message) error
    Platform() string
}
```

`Message` 只表达平台无关内容：

```go
type Message struct {
    Title string
    Text string
    Level string
    Status string
    Color string
    At []string
}
```

`factory.go` 只根据 platform 创建 sender，不读取业务请求。

### pkg/sender/dingtalk

职责：

- 构造钉钉 markdown payload。
- 使用 secret 生成签名 URL。
- 发送 HTTP 请求。

要求：

- secret 为空时不加签。
- webhook 日志必须脱敏。
- 响应非 2xx 或平台错误时返回安全错误。

### pkg/sender/feishu

职责：

- 构造飞书卡片 payload。
- 预留 secret 签名能力。
- 发送 HTTP 请求。

要求：

- 第一版如未实现飞书签名，配置文档必须说明。
- webhook 日志必须脱敏。

### pkg/template

职责：

- 加载模板文件。
- 注入时间格式化等模板函数。
- 渲染消息文本。

禁止模板读取外部文件路径以外的任意系统资源。

## 七、接口规范

### 健康检查

```text
GET /ping
```

响应：

```json
{
  "code": 200,
  "message": "操作成功",
  "data": {
    "message": "pong"
  }
}
```

### Alertmanager 通知

```text
POST /api/v1/alerts/alertmanager?channel=alert-prod&split=false
```

说明：

- body 使用 Alertmanager webhook 结构。
- `channel` 必填。
- `split` 可选，默认为 `false`。
- 不允许通过 query/body 传真实钉钉或飞书 webhook。

### Jenkins 通知

```text
POST /api/v1/notifications/jenkins
```

请求：

```json
{
  "channel": "jenkins-test",
  "status": "SUCCESS",
  "jobName": "cohort-build",
  "buildNumber": "123",
  "buildUrl": "http://jenkins/job/cohort-build/123/",
  "services": ["cohort-platform", "cohort-subject"],
  "branch": "release",
  "deployEnv": "test",
  "packageType": "image",
  "deploy": true,
  "deployType": "ssh",
  "triggerUser": "admin"
}
```

校验：

- `channel` 必填。
- `status` 必填，允许 `SUCCESS`、`FAILURE`、`ABORTED`、`UNSTABLE`。
- `jobName` 必填。
- `buildNumber` 必填。
- `buildUrl` 必填。

### Generic 通知

```text
POST /api/v1/notifications/generic
```

请求：

```json
{
  "channel": "ops-test",
  "title": "任务执行完成",
  "status": "SUCCESS",
  "level": "info",
  "content": "备份任务执行完成",
  "url": "https://example.com/tasks/1"
}
```

## 八、统一响应规范

成功：

```json
{
  "code": 200,
  "message": "操作成功",
  "data": {}
}
```

失败：

```json
{
  "code": 40001,
  "message": "channel is required",
  "data": null
}
```

错误码放在 `pkg/e`。业务错误由 service 返回，api 统一转换。

## 九、配置规范

配置值直接写入配置文件，示例配置只提交假值：

```yaml
server:
  address: ":8801"
  read_timeout_seconds: 10
  write_timeout_seconds: 10

auth:
  enabled: true
  token: "change-me"

channels:
  jenkins-test:
    platform: "feishu"
    webhook: "https://open.feishu.cn/open-apis/bot/v2/hook/example"
    secret: "SECexample"
    template: "jenkins_feishu"
    at: []

  jenkins-prod:
    platform: "dingtalk"
    webhook: "https://oapi.dingtalk.com/robot/send?access_token=example"
    secret: "SECexample"
    template: "jenkins_dingtalk"
    at: []
```

规则：

- `channel` 名称只能使用小写字母、数字、短横线和下划线。
- `platform` 第一版只允许 `dingtalk`、`feishu`。
- `webhook` 必填，但不得写生产真实值进仓库。
- `secret` 可选。
- `template` 可选，缺省时按事件来源和平台选择默认模板。

## 十、安全规范

- 默认开启接口鉴权。
- 支持 `Authorization: Bearer <token>`。
- 支持 `X-Webhook-Token: <token>`。
- token 比较使用恒定时间比较。
- 日志不得打印完整 webhook、secret、token。
- 第三方响应体如可能含敏感信息，日志中只记录状态码和安全摘要。
- 错误响应不得暴露内部配置、文件路径、堆栈。

## 十一、日志规范

建议记录：

- 服务启动和监听地址。
- 配置加载失败。
- 鉴权失败摘要。
- channel 不存在。
- 通知发送失败。
- 第三方平台返回非成功状态。

字段建议：

```text
source, channel, platform, status, request_id
```

禁止记录：

```text
webhook, secret, token, Authorization header
```

## 十二、模板规范

模板文件按来源和平台命名：

```text
<source>_<platform>.tmpl
```

示例：

```text
jenkins_dingtalk.tmpl
alertmanager_feishu.tmpl
```

模板只负责展示文本，不写业务判断。复杂规则放在 service 中归一化后传给模板。

## 十三、测试规范

必须优先补充单元测试的场景：

- channel 路由。
- Jenkins 请求校验。
- Alertmanager 事件转换。
- 钉钉签名。
- payload 构造。
- 敏感信息脱敏。
- 鉴权中间件。

外部平台调用测试使用 `httptest`，禁止依赖真实钉钉或飞书 webhook。

验证命令：

```bash
gofmt -w <changed-go-files>
go test ./...
git diff --check
```

核心流程变化增加：

```bash
go vet ./...
```

## 十五、依赖规范

新增依赖前必须说明：

- 使用目的
- 是否已有标准库或项目内替代方案
- 对构建和部署的影响
- 维护风险
- 安全风险

禁止为了少量代码引入大型框架。

## 十六、Git 与交付规范

- 默认不提交、不推送。
- 用户明确要求或确认方案包含提交步骤时，才执行 `git commit`。
- `git push` 必须单独确认。
- 提交前必须检查 `git status`、`git diff`、测试结果和敏感信息。
- 不提交构建产物、真实配置、日志和临时文件。

## 十七、修改后输出规范

每次修改后说明：

- 修改文件列表
- 修改内容摘要
- 本次修改影响范围
- 是否兼容已有功能
- 是否需要联动修改
- 是否已更新文档
- 验证结果
- 提交结果
- 推送结果
